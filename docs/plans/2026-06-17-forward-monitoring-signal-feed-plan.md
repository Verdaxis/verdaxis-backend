# Forward Curve Monitoring Signal Feed Plan

## Objective

Extend the existing Forward Curve monitoring board into a typed, read-only signal contract for:

- Executable bid/ask/orderbook context already present in `orderbook_orders`.
- Non-executable market indications, when a typed source row exists.
- Verdaxis fair-price bands, when a typed model/reference row exists.
- Physical stem availability, when a typed source row exists.
- Explicit no-feed/no-data states when those source rows do not exist.

This is a staging-only backend-first sprint. The frontend should consume the new contract after backend plan review and staging verification. Production rollout stays out of scope until user review.

Current `/api/curves/forward/board` already provides:

- Approved ports and canonical market products.
- Board cells keyed by `market_product + delivery_point_id + availability_window`.
- Benchmark midpoint context with source/demo provenance.
- Best bid, best ask, spread, depth, volume, and order count from active orderbook rows.
- Real/demo/unknown order counts and side-specific best-price source kinds.
- Focus curve and selected-slice depth.

Current frontend intentionally labels these as missing feeds:

- Indications.
- Physical stems.
- Fair-value band.

## Non-Goals

- Do not change `MarketTerminal`; it remains the trading/execution surface.
- Do not add direct Buy/Sell/Hit/Lift actions to Forward Curve.
- Do not infer indications, physical stems, or fair-price bands from demo seed prices, producer projects, benchmarks, or active orders.
- Do not expose organization IDs, account names, buyer/seller names, emails, vessel-linked party identifiers, or any counterparty identity in the monitoring response.
- Do not introduce broad ARA/region bucket curves, fuel-family curves, or certification-split curves in this sprint.
- Do not deploy to production.

## Contract Principles

All monitoring signals use the same canonical slice key:

```text
market_product + delivery_point_id + availability_window
```

Every returned signal object must include:

- `signal_type`: what the signal is.
- `signal_source_kind`: where the signal came from.
- `scope`: exactness of the market scope.
- `demo_status`: real/demo/mixed/unknown classification.
- `observed_at`: source observation timestamp, nullable only for no-data placeholders.
- `generated_at`: API response generation timestamp.

Response generation time must not be reused as source observation time.

Public responses must not expose raw feed identifiers or internal model identifiers. The board route is currently public, so the API contract may expose only:

- Signal/source classification enums.
- Real/demo/unknown counts.
- Timestamps.
- Sanitized allowlisted display labels generated by the frontend from enums.

The public JSON must never include raw `source`, `source_record_id`, `source_event_id`, `stem_uid`, `model_name`, `model_version`, `ingestion_run_id`, `trusted_ingestion_run_id`, `verified_by`, free-form `detail`, organization/account IDs, emails, vessel identifiers, or counterparty names.

## Signal Types

Add a signal-type enum-like schema value:

- `ORDERBOOK_BID`
- `ORDERBOOK_ASK`
- `BENCHMARK_MID`
- `MARKET_INDICATION`
- `FAIR_PRICE_BAND`
- `PHYSICAL_STEM`

`signal_type` is separate from `signal_source_kind`. For example, a physical stem can be `signal_type=PHYSICAL_STEM` and `signal_source_kind=DEMO_SEED` in demo mode, or `signal_source_kind=PHYSICAL_STEM` when it comes from a real typed source.

Do not widen the existing `MarketSourceKind` enum in this sprint. Existing board/orderbook/benchmark fields keep their current enum values and generated-client shape.

- `MARKET_INDICATION`
- `PHYSICAL_STEM`
- `FAIR_PRICE_MODEL`
- `DEMO_SEED`
- `MIXED_SOURCE`
- `NO_DATA`
- `UNKNOWN`

Missing feeds must return `signal_source_kind=NO_DATA`, not a fabricated demo/model value.

`MarketDemoStatus.NOT_APPLICABLE` already exists in backend and frontend types; this sprint should use the existing value rather than introduce a new demo-status enum value.

Add explicit enum schemas:

- `ForwardCurveIndicationSide`: `BID`, `ASK`, `MID`
- `ForwardCurvePhysicalStemStatus`: `AVAILABLE`, `TENTATIVE`, `ALLOCATED`, `CANCELLED`

## Data Model

Create `app/models/forward_monitoring.py` and import it from `app/models/__init__.py`.

Use append-friendly source tables so future ingestion can insert new observations without mutating historical rows.

Canonical key fields must be constrained in both application validation and SQLite/Postgres-compatible database checks:

- `market_product` must match the existing canonical market product enum values.
- `availability_window` must be `SPOT`, `YYYY-MM`, `YYYY-QN`, or `YYYY-CAL`.

For real/demo provenance, all new rows default to demo/unknown unless ingestion explicitly proves otherwise:

- `is_demo boolean not null default true`.
- `is_verified_real boolean not null default false`.
- `verified_real_at timestamptz null`.
- `trusted_ingestion_run_id uuid null`.
- A row may display as `REAL_ONLY` only when `is_demo=false`, `is_verified_real=true`, `trusted_ingestion_run_id is not null`, and the row joins to a trusted ingestion run created by the backend ingestion path for an allowlisted source in that signal family.
- Manual staging rows and seed/fixture rows cannot create trusted ingestion runs and cannot display as live real feed support, even if someone manually sets `is_demo=false`, `is_verified_real=true`, and an allowlisted `source` value.
- If no trusted ingestion writer exists yet, downgrade all non-demo/non-trusted rows to `UNKNOWN` and keep the `REAL_ONLY` display path disabled.

For ingestion idempotency:

- `source_record_id` means stable upstream record identity and may repeat across append observations of the same real-world object.
- `source_event_id` means unique upstream event/observation identity and, when present, must be unique per `source`.
- Internal source fields stay in database rows and logs only; they are not returned by `/curves/forward/board`.

### Board vs Focus Population Rules

`ports[].cells[]`:

- Uses the selected matrix `availability_window` only.
- Includes indication and stem summaries for that selected window.
- Includes `fair_price_band` for that selected window when a row exists.
- Includes `fair_price_band_provenance` for that selected window whether a band exists or not.
- Loads selected-window indication summaries once for the whole matrix, batched together with any required focus windows.
- Loads selected-window physical stem summaries once for the whole matrix, batched together with any required focus windows.

`focus.curve[]`:

- Uses all curve windows for the focused product and delivery point.
- Includes fair-price bands across all curve windows when rows exist.
- Includes `fair_price_band_provenance` for each curve window whether a band exists or not.
- Batch-loads indication and physical-stem summaries for all focus-curve windows in one query per signal family.
- Returns no-data indication/stem summaries only when the backend actually checked that exact focus-window slice and found no rows.
- Does not run one signal query per focus-curve window.

`focus.indications`, `focus.fair_price_band`, and `focus.physical_stems`:

- Use only the exact selected slice: focused product, focused delivery point, and selected matrix `availability_window`.
- `focus.indications` and `focus.physical_stems` are bounded lists for drilldown detail.
- `focus.fair_price_band` is the selected-slice band or `null`.
- `focus.fair_price_band_provenance` is the selected-slice provenance placeholder or populated band provenance.

Exact call topology for this sprint:

- One indication-summary query covering all selected-window matrix cells plus all focus-curve windows for the focused product/delivery point.
- One physical-stem-summary query covering all selected-window matrix cells plus all focus-curve windows for the focused product/delivery point.
- One fair-price-band query for the selected matrix window plus the focus-curve windows.
- One selected-slice indication detail query for focus.
- One selected-slice physical-stem detail query for focus.
- Zero per-cell and zero per-focus-window signal queries.

## Query Service

Create:

- `app/services/forward_monitoring.py`

Service functions:

- `load_indication_summaries(db, keys, lookback_days=7)`
- `load_latest_indications_for_focus(db, market_product, delivery_point_id, availability_window, limit=10)`
- `load_fair_price_bands(db, keys, lookback_days=30)`
- `load_physical_stem_summaries(db, keys, lookback_days=90)`
- `load_physical_stems_for_focus(db, market_product, delivery_point_id, availability_window, limit=10)`

Implementation rules:

- Batch by the full board key sets.
- Do not query per board cell.
- Do not fetch full signal history into Python for summaries.
- Use SQL window functions or aggregate subqueries that are compatible with current SQLite tests and Postgres deploys.
- Indication summaries use a bounded 7-day lookback and select the latest row per `(market_product, delivery_point_id, availability_window, side)` ordered by `observed_at desc, created_at desc, id desc`.
- Fair-price bands use a bounded 30-day lookback and select the latest row per `(market_product, delivery_point_id, availability_window)` ordered by `observed_at desc, created_at desc, id desc`.
- Physical stem summaries use a bounded 90-day lookback and select the latest row per `(market_product, delivery_point_id, availability_window, source, stem_uid)` ordered by `observed_at desc, created_at desc, id desc`, then aggregate only latest rows with `AVAILABLE` or `TENTATIVE` status.
- A later `CANCELLED` or `ALLOCATED` row for the same `(source, stem_uid)` removes the earlier available quantity from summary counts.
- Summaries include counts, quantity totals where applicable, latest price/band/stem values, provenance, and latest `observed_at`.
- Focus list queries are capped at 10 rows.
- Focus indication and stem detail queries are capped at 10 latest rows after the same slice filters and do not include raw internal identifiers in the serialized response.
- Lookback windows are constants in the service layer, not public query parameters in this sprint.
