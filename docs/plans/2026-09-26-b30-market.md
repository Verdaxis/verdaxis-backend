# B30 and B100 Market Implementation Plan

**Goal:** Add B30 and B100 to the existing exchange and all market discovery surfaces with fuel-specific supplier requirements.

**Architecture:** Reuse canonical product identity, order matching, trade lifecycle and market projections. Define one contract for each fuel so orders cannot match incompatible fuels. Reuse existing supplier metadata and apply one product-specific validation rule at every write and execution boundary.

**Tech Stack:** FastAPI, SQLAlchemy, PostgreSQL/Alembic; React, TypeScript and Vitest.

## Product decision

Code/name: B30. UUID: c4cecebc-3d2d-5840-8021-57a9a11bc673. Family: Biofuel. Grade: B30. Quantity: MT; existing 200 MT minimum.

Initial contract: 30% FAME by volume and 70% VLSFO; finished fuel ISO 8217:2024 RF 380, sulphur at most 0.50% by mass. This is the exchange contract for this book, not a claim that every fuel called B30 uses this composition. Other bases/grades cannot share this book. Supplier CI describes the whole delivered blend. Scheme selection is a supplier declaration, not verified batch evidence.

The user confirmed adding both B30 and B100. B100 code/name: B100. UUID: 74eb9cb5-f0e3-55f1-b82c-fe29b7c45bf5. Family: Biofuel. Grade: B100. Quantity: MT; 200 MT minimum. Contract: neat FAME biodiesel (not HVO), finished ISO 8217:2024 DFA; sulphur at most 0.10% by mass. Supplier CI describes the whole fuel and requires a calculation method. The two products have distinct IDs and cannot cross-match.

The user also requested seeded demo listings using current market prices. Research public assessment anchors with price/date/source, then use those anchors in the existing demo books and automatic refresh. Disclose any proxy ports, illustrative spreads and forward scenarios; never label synthetic quotes as observed executable prices.

## Work and checks

1. Backend catalog and qualification: app/market_catalog.py, app/services/execution_policy.py, app/routers/orderbook.py, app/routers/market_support.py, app/routers/inventory.py. Trace all callers; apply B30 rules to create/update/support/inventory and execution. Extend focused existing qualification/matching tests.
2. Market projections: remove four-alcohol assumptions in public filters, benchmarks, preferences and forward signal models. Add B30 to existing demo coverage with explicit demo prices and correct fuel metadata. Do not manufacture real quotes or compliance benefits. Test combined filters and existing curve/demo behavior.
3. Database: new forward migration catalog_20260926_biofuels after ua_20260926_activity_policy inserts both exact products, widens existing checks and preserves trade snapshot trigger protections. Add exact deployment checkpoints; validate upgrade, raw PostgreSQL trade write, snapshot rejection and downgrade refusal when B30 data exists.
4. Frontend shared catalog: types/options/labels, map port popup, map and public tickers, forward curve/insights, analytics and smoke scripts. Reuse catalog-driven selectors. Extend existing market utility and rendered tests.
5. Supplier form/details: show the B30 contract to both sides, use B30 specification and whole-blend CI guidance, retain current certification/SDS/feedstock/origin requirements. Reset fuel-specific fields when product changes or an old template is loaded. Translate new UI copy in English and Chinese.
6. Estimator: keep B30 selectable, but show a clear unavailable state when batch-specific inputs needed for a valid blended-fuel estimate are absent. Do not apply the existing zero-fossil model to B30.
7. Freeze edits, run backend and frontend acceptance checks, PostgreSQL migrations and role tests, then inspect the affected rendered UI. Run an independent review of matching/data boundaries and all requested surfaces.
8. Prepare reviewable branch/PR and release notes with research sources and limitations. Follow the existing guarded release process; production promotion requires task-specific authorization under the project deployment instructions.
